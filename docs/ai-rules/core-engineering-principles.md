# Core Engineering Principles

## 1. 「動く」と「運用に耐える」は別物

コードは、ローカルで動くだけでは不十分。

常に以下を考慮する。

- 本番データ規模で破綻しないか
- 数百件〜数万件のデータで性能劣化しないか
- null / 空配列 / 0 / 未設定値 / 不正値に耐えられるか
- 他テナント・他店舗・他ユーザーのデータ混入が起きないか
- 一覧取得・一括処理・CSV・バッチでメモリ爆発しないか
- 障害時に原因追跡できるか
- 将来の仕様変更に耐えられるか

## 2. フレームワークは道具であり、責務を壊す理由にはならない

フレームワーク固有の書き方よりも、まず設計上の責務を優先する。

ただし、フレームワークが標準で提供している機能は尊重する。

### 原則

- フレームワークが自動で行う処理を手動で再実装しない
- 標準のバリデーション・認証・認可・ルーティング・ORM機能を優先する
- フレームワークの思想に反する独自実装を避ける
- 標準機能を使うなら、その機能の責務内で完結させる
- 独自実装する場合は、理由・影響範囲・保守コストを明示する

## 3. 既存コードの意図を読む

一見非効率・冗長に見えるコードにも理由がある可能性を考える。

修正前に以下を確認する。

- なぜこのレイヤーに書かれているのか
- なぜこのデータ取得方法なのか
- なぜこの条件分岐があるのか
- なぜこの命名なのか
- なぜこのタイミングでAPIを呼んでいるのか
- フロントエンド・バックエンド・DB・外部APIのどこに影響するか

意図が読めないコードは、勝手に削除・置換しない。

## 4. 既存パターンを優先する

新しい正しさより、プロジェクト内の一貫性を優先する。

- 既存の命名規則を踏襲する
- 既存のディレクトリ構成を踏襲する
- 既存の責務分離を踏襲する
- 既存のテストパターンを踏襲する
- 独自の設計思想を勝手に持ち込まない

## 5. AIの役割

AIは実装速度を上げるために使う。

ただし、以下は人間が判断する。

- 本番データ規模での性能判断
- 業務ルールの正しさ
- 既存コードの意図
- データ関係性
- 運用上の例外
- 仕様の優先順位

AIが書いたコードについて、理由を説明できない場合は、そのまま採用しない。
