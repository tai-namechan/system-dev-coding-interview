# Code Context Awareness

## 原則

コードを変更する前に、必ず「なぜこのコードなのか」を考える。

既存コードは、冗長に見えても以下の意図を持っている可能性がある。

- パフォーマンス最適化
- 既存データの例外対応
- 他ユーザー・他テナント・他組織データ混入防止
- フロント側の都合
- 過去バグの再発防止
- 運用上の制約
- DB構造上の制約
- 大量データ対策

## 1. データ規模の想像

修正前に以下を考える。

- このテーブルは何件規模か
- APIレスポンスは何件返る可能性があるか
- 一覧取得か単体取得か
- ページネーションはあるか
- 1000件以上になり得るか
- 数万件になった場合も耐えられるか
- フロントに全件返していないか
- メモリ上に全件展開していないか

## 2. データ取得パターンの尊重

既存の取得方法を安易に変えない。

### Eager Load

Eager Load には理由がある。

- N+1 防止
- response schema / serializer 側で relation を使う
- フロント表示に必要
- 後続処理で参照する

### Lazy Load

Lazy Load にも理由がある可能性がある。

- 常に必要なデータではない
- 件数が少ない
- 条件によって必要になる
- 初期表示を軽くしたい

### select / columns

カラムを絞っている場合、以下の意図があり得る。

- 通信量削減
- メモリ削減
- 不要な情報を返さない
- フロント依存を最小化
- セキュリティ上の理由

変更する場合は、必要な外部キーを欠落させない。

## 3. フロント ↔ バックエンド間のデータフロー

レスポンス構造の変更は影響範囲が大きい。

確認すること:

- Response Schema で整形しているか
- フロント側でフィルタ・ソート・加工しているか
- API response の型が変わらないか
- optional / nullable の扱いが変わらないか
- API利用箇所が複数ないか
- OpenAPIの仕様が変わらないか

## 4. 意図不明コードの扱い

以下に該当する場合は、勝手に変更しない。

- なぜ必要か分からない条件分岐
- 一見不要に見える where
- 一見不要に見える join
- 一見不要に見える eager load
- 一見冗長な null check
- 一見冗長なスコープチェック
- 過去バグ対策に見える処理
- コメントがなく意図が推定できない処理

この場合は、以下を報告する。

- 意図不明な箇所
- 想定される理由
- 変更した場合のリスク
- 確認したい内容

## 5. 修正提案時の報告義務

修正提案時は、必ず以下を含める。

### データ規模への影響

- 大量データ時に遅くならないか
- 1000件以上で破綻しないか
- ページネーションが必要ではないか

### メモリへの影響

- 全件取得していないか
- メモリ上に全件展開していないか
- chunk / cursor / streaming が必要ではないか

### SQLへの影響

- クエリ数が増えていないか
- N+1 が発生していないか
- JOIN / IN / subquery の選択理由
- スコープ条件が効いているか

### 既存パターンとの整合性

- 既存の取得パターンを壊していないか
- 既存の命名規則を守っているか
- 既存の Service / Repository の使い方に合っているか

### 意図不明コードの有無

- 変更対象に意図不明コードがあるか
- そのコードを変更するか、残すか
- ユーザー判断が必要か
