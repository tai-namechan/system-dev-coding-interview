# AI Response Format

## 原則

AIはすぐにコードを書き換えず、まず現状理解・影響範囲・懸念点を整理する。

小さな typo や明らかなバグ修正を除き、以下のフォーマットで回答する。

## Step 1. 現状理解

以下を簡潔に説明する。

- 対象ファイル
- 対象処理の責務
- 現在の処理の流れ
- 既存コードの意図の推定
- 関連する Router / Service / Repository / Schema
- 影響しそうな画面・API・テスト

## Step 2. 修正方針

以下を必ず含める。

- 何を変更するか
- 何を変更しないか
- Router / Service / Repository の責務分離に合っているか
- 既存パターンと合っているか
- データ規模への影響
- メモリへの影響
- SQLへの影響
- N+1 の有無
- スコープ条件の有無
- APIレスポンスへの影響
- テスト方針
- ユーザー確認が必要な箇所

## Step 3. 実装

実装時のルール。

- 差分は最小にする
- 関係ない整形をしない
- 共通部品を不用意に変更しない
- 既存命名を踏襲する
- 既存の責務分離を守る
- 新しい抽象化を勝手に増やさない
- 既存テストがある場合はそのパターンに合わせる

## Step 4. テスト・確認

以下を報告する。

- 追加したテスト
- 変更したテスト
- 実行すべきテストコマンド
- 手動確認すべきAPI・画面
- 確認したエッジケース
- 未確認のリスク

## 判断に迷う場合

判断に迷う場合は、実装を進める前に以下を提示する。

- 選択肢A
- 選択肢B
- それぞれのメリット
- それぞれのリスク
- 推奨案
- ユーザーに確認したいこと

## 禁止

- 理由を説明せずに大きく書き換える
- 既存構造を無視して独自設計にする
- DBクエリの影響を説明しない
- 全件取得の可能性を無視する
- N+1 の可能性を無視する
- スコープ条件を確認しない
- テストで外部HTTPが飛ぶ可能性を残す
- 意図不明コードを黙って削除する
