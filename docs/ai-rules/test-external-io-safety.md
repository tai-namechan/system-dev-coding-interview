# Test & External IO Safety

## 1. テストの基本方針

テストは「仕様書」として読めるレベルを目指す。

単にカバレッジを上げるためではなく、以下が分かるように書く。

- 何を検証しているか
- どの条件で
- どの入力に対して
- どの出力を期待するか
- どの業務仕様を守っているか

## 2. 既存テストパターンを優先する

新規テストは既存テストの書き方に合わせる。

確認すること:

- pytest fixture の使い方
- TestClient / AsyncClient の使い方
- DB fixture の扱い
- dependency override の使い方
- 認証ユーザーの作り方
- factory の使い方
- assert の粒度
- transaction / rollback の扱い

既存テストと乖離する書き方をしない。

## 3. テストケース設計

正常系だけで終わらせない。

最低限確認する。

- 正常系
- null
- 空配列
- 0
- 未存在ID
- 他ユーザー・他テナント・他組織データ
- 権限なし
- バリデーションエラー
- データ件数が多い場合
- 重複データ
- 境界値

## 4. 外部HTTP禁止

テストでは外部HTTPを絶対に投げない。

外部API通信が絡む実装変更では、必ず mock / fake / stub を使う。

禁止:

- テストで実HTTPを投げる
- 本物の外部APIキーを使う
- `.env` の秘密情報に依存する
- 外部サービスの状態に依存するテストを書く

## 5. 外部HTTP mock

HTTP mock の対象URL・ドメインは、実コードと同じ設定値を参照する。

禁止:

- テスト側だけでURLをベタ書きする
- 実コードと異なるドメインを mock する
- mock 漏れがある状態でテストを通す
- 外部APIへ実リクエストが飛ぶ可能性を残す

## 6. mock 漏れの可能性がある場合

mock 漏れの可能性がある場合、いきなり実装しない。

まず以下を提案する。

- 原因
- 統一案
- 影響範囲
- 追加テスト
- mock対象URL
- 外部HTTP禁止ガードの設置場所

## 7. テスト変更時の報告

テストを追加・変更した場合、必ず以下を報告する。

- 追加したテストケース
- 既存テストパターンとの整合性
- 外部HTTPが発生しない保証
- 他ユーザー・他テナント・他組織データ混入を防げているか
- DB状態の検証内容
- 未検証のリスク
